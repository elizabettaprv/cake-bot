# Cake-bot

Бот-консультант первой линии для кондитерской: отвечает на вопросы клиентов, собирает данные заказа и передаёт человеку то, что не должен решать сам.

## Задача

- Кондитерская в городе X (Испания), доставка в радиусе 100 км.
- Языки: русский и испанский. Клиенты пишут онлайн откуда угодно, заказы принимаются только в зоне доставки.

- Объём: 100–140 обращений в неделю (15–20 в день). Цифры предварительные.
- Сейчас отвечает человек по шаблонам. Цель — снять с него повторяющиеся вопросы.

## Метрики успеха

- Доля обращений, закрытых без человека. Целевое значение определим после evals.
- Полнота данных лида (заказа).
- Ноль ошибочных ответов в зоне риска (аллергены): ошибка здесь стоит здоровья клиента.

## Архитектура v1

- Workflow, а не автономный агент.
- Двухслойный роутер: сначала правила (бесплатно и предсказуемо), затем LLM-классификатор для того, что правила пропускают (другой язык, опечатки, перефразы).
- Если сработало правило, классификатор не вызывается: `risk` сразу уходит человеку, `stop` сбрасывает диалог.
- Классификатор выбирает одну из пяти меток: `risk`, `order`, `facts`, `general`, `other`.
- No match: если ответ классификатора не входит в список меток, код не доверяет ему и передаёт диалог человеку или задаёт уточняющий вопрос. Непонятное не сваливается в «общие вопросы».
- Ветка заказа работает как слот-филлинг: бот уточняет только незаполненные поля заказа.
- Три рубежа защиты по аллергенам: правила → LLM-классификатор → база знаний, где аллергены помечены «отвечает только человек».

```
Сообщение
  │
  ▼
rules.py
  ├─ risk  → человеку, классификатор не вызываем
  ├─ stop  → сброс диалога
  └─ None  → дальше
                │
                ▼
         LLM-классификатор
           ├─ risk     → человеку
           ├─ order    → заказ (слот-филлинг)
           ├─ facts    → факты бизнеса + мостик к заказу
           ├─ general  → общий вопрос
           ├─ other    → не про кондитерскую
           └─ no match → уточнить или человеку
```

### Метки классификатора

| Метка | Когда | Не сюда, если |
|---|---|---|
| `risk` | Аллергия, аллергены, безопасность, вопросы о составе. | Исключений нет: `risk` побеждает любую другую метку. |
| `order` | Намерение купить: дата, количество, «хочу», «можно заказать». | Только цена или описание → `facts`; есть сигнал риска → `risk`. |
| `facts` | Ответ требует нашей базы знаний: меню, цены, часы работы, доставка. | Есть намерение купить → `order`; есть сигнал риска → `risk`. |
| `general` | Ответ не зависит от нашей кондитерской: общие кулинарные знания. | Про наши товары или цены → `facts`; есть сигнал риска → `risk`. |
| `other` | Не относится к кондитерской: приветствие, погода, спам. | Есть любой сигнал из веток выше. |

Граница `facts` / `general` проверяется одним вопросом: можно ли ответить без нашей базы знаний? Нельзя → `facts`, можно → `general`.

`other` и no match — разные вещи. `other` модель выбирает сама: сообщение понятно, но не про кондитерскую. No match ловит код: модель вернула что-то вне списка меток.

## Ключевые решения

**Workflow, а не автономный агент.**
Сценарии обращений известны заранее, а часть вопросов связана со здоровьем клиента (аллергены). Путь обработки задаёт код, а не модель: так поведение бота предсказуемо и его можно проверить тестами. Автономия модели здесь добавляет риск, но не добавляет пользы.

Модель принимает решение в одной точке: LLM-классификатор выбирает метку (паттерн routing). Что происходит дальше в ветке, решает код. Агентного цикла, где модель сама выбирает следующий шаг и вызывает инструменты, в v1 нет намеренно. В ветке заказа модель извлекает данные из сообщений по JSON-схеме, но достаточно ли их, проверяет код по обязательным полям: такая проверка всегда одинаковая и покрывается тестами.

**Мягкие и жёсткие ограничения вместе.**
Схема и список допустимых меток есть в промпте (мягкое ограничение, работает почти всегда), а код проверяет результат модели (жёсткое ограничение, работает всегда): метка должна входить в список, заказ должен содержать все обязательные поля, при `risk` диалог уходит человеку, мостик к заказу дописывает код.

**Один бот, без мультиагентной схемы.**
Задача не настолько сложная, чтобы делить её между несколькими агентами. Лишние вызовы моделей увеличивают стоимость и время ответа, ничего не давая взамен.

**Риски ищем широко, команду «стоп» — узко.**
Правила для `risk` ищут по части слова («орех», «аллерг»), чтобы поймать все формы. Лишнее срабатывание здесь дешёвое: вопрос просто уйдёт человеку. Правила для `stop` ищут только целое слово, чтобы «стопка блинчиков» не сбрасывала диалог. Лишнее срабатывание здесь дорогое: клиент теряет уже собранный заказ.

Решаем по данным evals.

**`risk` побеждает любую другую метку.**
Если в сообщении есть сигнал риска, остальные интенты не важны: «торт с орехами на субботу» уходит человеку, хотя это заказ. Исключений нет.

**Вопросы о составе уходят человеку.**
Любой вопрос о составе («из чего медовик?») относится к `risk`, даже если клиент просто интересуется. В ответе о составе почти всегда есть аллергены (мёд, яйца, молоко, мука), а бот об аллергенах не говорит. Цена решения: ниже доля обращений, закрытых без человека. Пересмотрим после evals.

**Классификатор не обязан быть идеальным, если его ошибки дёшевы.**
Ветки устроены так, что ошибка между `facts` и `order` обратима: бот отвечает на заданный вопрос, а ветка `facts` заканчивается мостиком к заказу («Хотите оформить? Подскажите дату»). Мостик дописывает код, а не модель: текст проверен заранее и срабатывает всегда. Мостик допустим только там, где ошибка обратима, поэтому в `risk` его нет.

## Статус

Готово:
- `rules.py`: функция `detect_rule_intent`, возвращает `risk`, `stop` или `None`.
- Подключение к Claude API: ключ лежит в `.env` и не попадает в репозиторий.
- `first_call.py`: первый вызов модели, проверка `stop_reason`.
- Спецификация меток классификатора (см. «Метки классификатора»).

Дальше:

## Идеи для v2

- Multi-label классификация: сообщение может получить несколько меток (`order` + `risk`). Приоритет `risk` сохраняется, но оператор получает контекст («заказ на субботу, торт с орехами, проверить аллергены»). Проверка пользы: меньше уточняющих вопросов у оператора.
